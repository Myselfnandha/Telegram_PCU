## 1. Overview & Architecture

Phase 01 establishes the foundational multi-tenant data layer for TG Power Suite v3.0. Prior to this implementation, all configuration, state, and credentials were bound to global singletons and local SQLite files that did not survive container destruction on ephemeral cloud platforms like Render.com.

The new data foundation provides:
- **Async SQLAlchemy 2.0 Engine**: Fully asynchronous connection pooling and transaction lifecycle.
- **Dialect Agnostic**: Seamlessly switches between PostgreSQL (`postgresql+asyncpg://...`) for cloud/production and SQLite (`sqlite+aiosqlite://...`) for local development and rapid test isolation.
- **Alembic Versioning**: Schema version control located at `backend/alembic/` with autogenerated migration scripts.
- **Tenant-Aware Repositories**: Data access methods enforcing ownership boundaries at both application and database levels.

## 2. Core Entities & Schema Definition

The schema defines 8 interconnected entities designed for zero-leakage multi-tenancy:

| Entity Name | Primary Key | Key Columns / Constraints | Purpose |
| :--- | :--- | :--- | :--- |
| `app_users` | UUID | `display_name`, `status`, `role`, `created_at` | Tenant identities with status and RBAC controls. |
| `login_credentials` | UUID | `user_id` (FK), `credential_type`, `credential_data` | Passkeys, WebAuthn credentials, and recovery keys. |
| `trusted_devices` | UUID | `user_id` (FK), `display_name`, `public_key`, `verified_at`, `revoked_at` | Approved hardware devices authorized to stream. |
| `app_sessions` | UUID | `user_id` (FK), `device_id` (FK), `token_hash` (Unique), `expires_at`, `revoked_at` | Server-managed, revocable user sessions. |
| `telegram_accounts` | UUID | `owner_user_id` (FK), `telegram_user_id` (Global Unique), `role` (`primary`/`turbo`), `status` | Registered Telegram accounts bound to tenants. Enforces one primary account per owner. |
| `telegram_session_vault` | UUID (FK) | `ciphertext`, `nonce`, `key_version`, `session_version` | AES-256-GCM encrypted Telegram credentials. |
| `telegram_client_leases` | UUID (FK) | `owner_instance_id`, `fencing_epoch`, `expires_at` | Concurrency fencing to prevent split-brain client workers. |
| `audit_events` | UUID | `user_id` (FK), `telegram_account_id`, `event_type`, `metadata_json` | Append-only security and access audit log. |

### Enforced Constraints & Invariants:
1. **Global Telegram User ID Uniqueness**: A Telegram user account (`telegram_user_id`) cannot be claimed by or linked to more than one application user (`owner_user_id`).
2. **Single Primary Account Per Tenant**: A partial unique index (`uq_owner_primary_account`) enforces that each tenant can register at most one account with `role = 'primary'`.
3. **Cascading Teardown**: Deleting an application user (`app_users`) automatically purges their credentials, devices, sessions, and linked Telegram accounts.
